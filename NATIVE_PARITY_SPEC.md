# NATIVE_PARITY_SPEC — «Замер потолков»

## 1. Статус документа

Этот документ задаёт контракт для ПОЛНОЦЕННОЙ нативной Android-миграции приложения «Замер потолков».

Главный эталон поведения и внешнего вида — `webapp/index.html`.
Утверждённый SHA-256 эталона:

`354fbede167490d2481d3253507ff2829dcefec495298075487880ea2258a388`

Текущий web golden master: APP_BUILD_VERSION `184-gesture-fix`.

Нативная версия НЕ должна использовать WebView как рабочий UI и НЕ должна запускать HTML/JS как приложение.
HTML/CSS/JS остаётся неизменяемым golden master только для аудита, сравнения и регрессионных тестов.

Этот документ задаёт МИНИМАЛЬНЫЙ известный parity-контракт. Astra обязана перед началом переноса полностью прочитать golden master и ДОПОЛНИТЬ спецификацию всеми обнаруженными функциями, состояниями, жестами, текстами, стилями, расчётами и граничными случаями. Ничего из этого документа удалять нельзя.

## 2. Определение «точной копии»

«Точная копия» означает функциональную и визуальную эквивалентность, а не «похожий дизайн».

Для каждого экрана/состояния должны совпадать:
- информационная архитектура;
- порядок блоков;
- тексты и подписи;
- кнопки, меню и модальные окна;
- размеры и взаимное расположение ключевых элементов;
- состояния selected/disabled/expanded/collapsed;
- прокрутка;
- жесты;
- долгие нажатия;
- ввод размеров;
- анимации;
- вибрации;
- сохранение состояния;
- формулы и округление;
- правила автопривязки;
- ошибки/валидация;
- PDF/backup поведение;
- поведение после перезапуска приложения.

Любая функция, которая есть в golden master и отсутствует в native, считается FAIL.
Любое изменение логики «ради нативности» считается FAIL.
Любое «улучшение UX» без отдельного запроса пользователя считается FAIL.

## 3. Архитектурные ограничения native

Разрешено:
- Kotlin;
- Jetpack Compose для обычных экранов/панелей;
- собственный native Canvas/View/Compose Canvas для чертежа;
- DataStore/Room/файловое хранилище, если внешнее поведение и данные сохраняются корректно;
- Android vibration/haptics;
- Android Storage Access Framework / MediaStore;
- нативная генерация PDF либо точный локальный эквивалент при полном совпадении результата.

Запрещено:
- WebView как рабочий интерфейс;
- HTML/JS runtime внутри финального приложения;
- удалённые CDN/шрифты/скрипты;
- переписывание «по смыслу» без проверки parity;
- создание нового дизайна;
- замена custom-клавиатуры системной клавиатурой;
- потеря старых сохранений без явной стратегии миграции.

Для drawing engine предпочтителен отдельный `CeilingDrawingView`/эквивалентный native слой с собственной системой координат, zoom/pan, hit-testing, snapping и label transforms. Реализация может отличаться внутренне, но поведение должно совпадать.

## 4. Состояние и совместимость данных

Golden master использует существующую схему сохранения и миграций. Native-аудит должен ДО переноса определить:
- `APP_STORAGE_KEY`;
- `APP_SCHEMA_VERSION`;
- полную JSON-структуру заказа;
- структуру комнаты;
- стены/точки/диагонали;
- состояние dimension labels;
- цены/материалы;
- UI settings;
- историю/сохранённые замеры;
- все migration steps.

До начала native-кода Astra обязана задокументировать точные поля, типы, nullable/default значения и миграции.

Если старые данные из WebView/localStorage невозможно импортировать напрямую после установки новой native-версии, должен быть предусмотрен детерминированный путь миграции через существующий JSON backup без потери данных.

## 5. Главный экран / заказ

Обязательное поведение:
- создание заказа;
- удаление заказа;
- имя клиента является названием заказа;
- телефон;
- адрес;
- отсутствие функции «номер заказа»;
- текущий заказ;
- сохранение данных автоматически;
- active order id не является persisted field: после полного relaunch golden master выбирает `db.orders[0]`;
- порядок и подписи блоков должны повторять golden master;
- раскрытие/сворачивание секций повторяет golden master.

Нативная версия не должна автоматически добавлять новые поля.

## 6. Комнаты

Обязательное поведение:
- список комнат в текущем заказе;
- добавить комнату;
- выбрать комнату;
- long press/удержание по комнате открывает меню;
- переименовать;
- дублировать;
- удалить;
- индикатор завершённости, если он есть в golden master;
- одна рабочая схема/чертёж на комнату;
- горизонтальная компоновка маленьких карточек/квадратов как в эталоне;
- активная комната сохраняется только в runtime текущей сессии;
- после полного relaunch golden master открывает первую комнату первого заказа;
- после переключения комнаты в рамках текущей сессии её чертёж и расчёты восстанавливаются без изменений.

## 7. Режимы чертежа

Должны существовать и работать независимо:
- Стена;
- Точки;
- Диагональ;
- Цифры.

Режим по умолчанию и логика переходов должны совпасть с golden master.

После замыкания контура quick-control режима «Стена» блокируется, как в golden master v184.
При закрытом контуре нельзя создавать продолжение стены/«хвост» за точкой замыкания.

## 8. Рисование стен

Критические правила:
- первая стена может начинаться из разрешённой пустой области так, как в эталоне;
- последующие стены начинаются только от существующих углов/концов;
- одна стена — один жест;
- новая точка создаётся только при смене направления/в предусмотренных случаях;
- после замыкания контура новые стены запрещены;
- никакой лишней линии после замыкания;
- редактирование существующей стены доступно по удержанию стены/размера;
- ввод длины не должен менять геометрию неожиданным способом;
- undo/redo должны восстанавливать точное предыдущее состояние;
- fit/центрирование работает как в web.

## 9. Размер стены и custom-клавиатура

Обязательно сохранить:
- собственную цифровую клавиатуру;
- без системной клавиатуры;
- начальное отображение `0`;
- ввод по long press/удержанию элемента;
- десятичная запятая там, где она предусмотрена;
- backspace/delete;
- явный `×` для закрытия;
- tap outside закрывает;
- корректное значение сохраняется;
- некорректное значение не должно молча разрушать данные;
- увеличенная touch-area без визуального увеличения;
- экранные единицы остаются такими, как в golden master.

## 10. Пользовательская шкала расчёта

Это проектное правило, его нельзя «исправлять» по стандартным единицам.

Контрольный пример:
- квадрат;
- четыре стороны по 500;
- площадь = 25 м²;
- периметр = 20 м.

Подписи единиц могут оставаться «мм» согласно текущему приложению. Нельзя переинтерпретировать этот масштаб без прямого запроса.

## 11. Zoom, pan и прокрутка

Критический touch-контракт:
- zoom двумя пальцами;
- pan двумя пальцами;
- одиночные жесты рисования не должны конфликтовать с zoom/pan;
- в режиме «Стена» вертикальный page scroll над drawing surface заблокирован;
- исключение — выделенная правая полоса шириной 74 px, где вертикальная прокрутка страницы разрешена;
- при открытом контуре page scroll разрешён только через правую HTML-полосу 74 px;
- после замыкания контур получает отдельный scroll-контракт: вертикальный one-finger drag непосредственно над SVG может вручную прокручивать страницу при порогах v184;
- в остальных режимах поведение прокрутки должно совпадать с golden master;
- никаких системных text-selection/context-menu при удержании элементов чертежа.

## 12. Snapping / 90° / направляющие / лупа / вибрация

Сохранить:
- лупу в режимах, где она есть;
- уменьшенный/тонкий визуальный стиль лупы как в эталоне;
- направляющие совпадения концов;
- красную направляющую по всем нужным направлениям;
- притягивание к направляющей;
- распознавание 90°;
- визуальный маркер 90°;
- короткую вибрацию при 90°;
- короткую вибрацию при snap/совпадении;
- соответствующее поведение на сложных углах;
- одинаковые пороги/ощущение, насколько это возможно после замера из исходного кода.

Astra обязана извлечь из web точные пороги snapping и dead zones и зафиксировать их в audit.

## 13. Точки

Режим «Точки» должен повторять golden master:
- создание/редактирование только в допустимых условиях;
- hit areas;
- лупа;
- snapping;
- undo/redo;
- влияние на контур;
- сохранение.

Точные правила Astra обязана дополнить после чтения исходника.

## 14. Диагонали

Сохранить:
- ручное создание/выбор диагонали;
- автодиагональ/расчёт там, где он предусмотрен;
- ручной ввод;
- редактирование по удержанию;
- удаление;
- явный `×` в модальном вводе;
- подпись диагонали внутри контура;
- отсутствие лишней рамки вокруг числа;
- корректное восстановление после zoom/redraw/save/relaunch;
- вибрацию/snapping при выборе точек, если это есть в эталоне.

## 15. Режим «Цифры»

Каждая размерная подпись должна иметь независимое состояние:
- положение X/Y;
- rotation 0–360°;
- size/scale;
- drag;
- поворот круговым контроллером;
- изменение размера `− / +`;
- reset размера, если он есть;
- сохранение после redraw;
- сохранение после zoom;
- сохранение после смены комнаты;
- сохранение после закрытия приложения;
- отсутствие «усыхания» подписи при drag;
- визуальный размер на экране не должен непреднамеренно меняться из-за camera zoom.

## 16. Буквы и подписи

Сохранить действующую логику:
- подписи стен/точек находятся снаружи контура, кроме диагональных значений;
- «скрыть буквы» скрывает именно буквы, сохраняя необходимые числа;
- отдельная функция добавления угла A, если присутствует в текущем golden master;
- не вводить новые буквенные режимы без запроса.

Astra должна подтвердить точную текущую реализацию по исходнику.

## 17. Площадь и периметр

Сохранить:
- расчёт текущей комнаты;
- площадь;
- периметр;
- округление/форматирование;
- пересчёт после геометрических изменений;
- общий итог по комнатам, если он есть;
- отсутствие дублирования/пересечения чисел;
- отсутствие единицы «мм» возле периметра, если это текущий утверждённый вид.

Все формулы должны быть перенесены по исходному коду, а не переписаны «математически правильнее».

## 18. Сохранённые замеры

Обязательно:
- автоматическое сохранение;
- окно/экран сохранённых замеров;
- поиск по имени;
- поиск по телефону;
- поиск по адресу;
- recent/all, если присутствует;
- удаление через action menu;
- список скроллится вертикально, даже если gesture начинается на карточке;
- нижняя навигация остаётся видимой;
- последняя карточка не перекрывается нижней навигацией;
- открытие сохранённого замера восстанавливает все комнаты, чертежи, цены и UI state.

## 19. Материалы / закупочный расчёт / смета

Сохранить текущие позиции и формулы, включая известный минимум:
- квадратура/полотно;
- багет;
- вставка;
- светильники;
- карниз;
- углы;
- трубы;
- световые линии;
- теневой профиль;
- керамогранит;
- пользовательские материалы;
- дополнительные материалы;
- дюбель автоматически 6 шт/м;
- расчёт по текущей комнате;
- расчёт по всем комнатам;
- ручной ввод цен;
- preset/default цены, если есть;
- сворачиваемые блоки, если есть;
- выбранные позиции;
- общий итог;
- объединённые заказы, если они реально есть в golden master.

Нельзя добавлять позиции, которых нет в эталоне, без запроса.

## 20. Клиентская смета

Сохранить:
- отдельный экран/режим;
- текущую структуру;
- текущие подписи;
- аккуратный светлый premium PDF;
- только выбранные позиции;
- компактную верстку без лишнего воздуха;
- корректные итоги;
- данные клиента/объекта, если они присутствуют;
- имя файла/формат, если он задан;
- валидный PDF с заголовком `%PDF-`.

Native PDF может быть реализован нативно, но визуальное сравнение с эталонным PDF обязательно.

## 21. Backup / restore

Сохранить:
- экспорт JSON;
- импорт JSON;
- полное восстановление заказа/комнат/чертежей/цен/настроек согласно текущему формату;
- валидацию файла;
- отсутствие потери существующих данных без подтверждения;
- совместимость с backup из golden-master web app.

Native обязан уметь принять backup, созданный текущей web-версией.

## 22. Настройки интерфейса

Сохранить текущие:
- font family;
- font size;
- font weight;
- night mode отсутствует в актуальном v184 и не должен добавляться на этапе parity; `applyUiPrefs` удаляет `ui-dark`;
- связанные UI settings;
- persistence после relaunch.

Никаких новых тем/редизайна на этапе parity.

## 23. Нижняя навигация

Сохранить текущую функциональную структуру и поведение.
Нижняя навигация:
- не должна перекрывать основной контент;
- не должна прыгать при клавиатуре/модалке;
- должна иметь safe-area отступ Android;
- кнопки работают так же, как в web;
- изменения названий/порядка запрещены без отдельного запроса.

Точный состав кнопок Astra фиксирует после аудита исходника.

## 24. Анимации

Перенести:
- длительности;
- easing/характер перехода;
- открытие/закрытие секций;
- модалки;
- bottom sheet;
- появление клавиатуры;
- смену активных состояний.

Если web-анимация не может быть повторена буквально, native должна быть визуально эквивалентной и измерена side-by-side.

## 25. Haptics

Haptic feedback не является декоративным.
Нужно перенести все места, где web вызывает `navigator.vibrate` или эквивалент:
- 90°;
- snapping;
- другие реальные триггеры из исходника.

Astra должна составить таблицу trigger → duration/pattern → native Haptic/Vibrator implementation.

## 26. Launcher icon

Единственный источник:
`branding/app_icon_master_1024.webp`

Не перерисовывать.
Разрешена только техническая подготовка Android adaptive/legacy launcher resources с сохранением композиции.

## 27. Visual parity procedure

Для каждого основного экрана/состояния Astra должна:
1. получить эталонное состояние web app;
2. получить native screenshot на том же размере viewport;
3. сравнить side-by-side;
4. при возможности сделать pixel/diff overlay;
5. записать отклонения;
6. исправить;
7. повторить до PASS.

PASS нельзя ставить только по субъективному «похоже».

Обязательные screenshot states:
- пустой новый заказ;
- заказ с клиентом;
- комнаты;
- drawing blank;
- drawing open contour;
- drawing closed contour;
- wall keypad;
- diagonal modal;
- numbers edit;
- saved measurements;
- materials/calc;
- client estimate;
- settings;
- night mode.

## 29. Миграционная последовательность

Нельзя переносить всё одним большим rewrite.

Фазы:
- Phase 0 — audit only, никаких native изменений;
- Phase 1 — data model + persistence + migration/backup contract;
- Phase 2 — app shell, typography, colors, safe areas, navigation;
- Phase 3 — orders + rooms;
- Phase 4 — drawing engine base + coordinate system + render;
- Phase 5 — wall/points gestures + closure + undo/redo;
- Phase 6 — zoom/pan/scroll contract + magnifier/snapping/haptics;
- Phase 7 — diagonals;
- Phase 8 — numbers/labels;
- Phase 9 — calculations/materials;
- Phase 10 — saved measurements;
- Phase 11 — backup/restore;
- Phase 12 — PDF/client estimate;
- Phase 13 — settings/night mode;
- Phase 14 — full visual/behavior parity regression;
- Phase 15 — signed/release-ready packaging after user acceptance.

После каждой фазы mandatory gate:
- build;
- automated tests;
- screenshot/behavior parity;
- matrix updated;
- no regressions in already-PASS phases.

## 30. Правило Phase 0

На Phase 0 Astra НЕ ИМЕЕТ ПРАВА:
- создавать native UI;
- удалять WebView wrapper;
- менять golden master;
- менять storage;
- начинать Compose screens;
- «готовить» новый дизайн.

Она должна только изучить исходник и документы и вернуть полный audit package:
- inventory screens/states;
- component map;
- function map;
- data schema;
- storage migration map;
- gesture map;
- haptic map;
- calculation/formula map;
- PDF/backup map;
- visual tokens;
- exact web implementation references;
- completed `NATIVE_MIGRATION_MATRIX.md`;
- список неясностей/UNVERIFIED.

## 31. Reconciled source-of-truth corrections after Phase 0
