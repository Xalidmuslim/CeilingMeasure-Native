ASTRA MAX — НАТИВНАЯ МИГРАЦИЯ «ЗАМЕР ПОТОЛКОВ»
PHASE 0: ТОЛЬКО ПОЛНЫЙ АУДИТ. НЕ НАЧИНАТЬ ПЕРЕПИСЫВАНИЕ.

ЦЕЛЬ ПРОЕКТА
Нужно в дальнейшем создать ПОЛНОЦЕННОЕ НАТИВНОЕ Android-приложение — точную функциональную и визуальную копию текущего web-приложения `webapp/index.html`.

Финальная native-версия НЕ должна быть WebView-оболочкой и НЕ должна использовать HTML/JS как рабочий UI.
Но сейчас, на Phase 0, НИЧЕГО НАТИВНОГО НЕ ПИШИ.

ГЛАВНЫЙ ЭТАЛОН
`webapp/index.html`

Ожидаемый SHA-256:
`354fbede167490d2481d3253507ff2829dcefec495298075487880ea2258a388`

Сначала вычисли SHA самостоятельно.
Если SHA не совпадает — STOP, ничего не менять, сообщить расхождение.

ОБЯЗАТЕЛЬНО ПРОЧИТАТЬ ПОЛНОСТЬЮ
1. `webapp/index.html`
2. `NATIVE_PARITY_SPEC.md`
3. `NATIVE_MIGRATION_MATRIX.md`
4. `FEATURE_CONTRACT.md`
5. `README.md`
6. `scripts/verify_webapp.py`
7. текущий Android wrapper, но только как справочный legacy-код;
8. все workflow GitHub Actions, связанные с приложением.

ВАЖНО О FEATURE_CONTRACT
Если в `FEATURE_CONTRACT.md` есть старое требование «Android APK must WRAP this app / WebView», считай его LEGACY-правилом текущей промежуточной APK-оболочки.
Для новой native-миграции архитектурный приоритет имеет `NATIVE_PARITY_SPEC.md`.
При этом все функциональные требования FEATURE_CONTRACT сохраняются и должны попасть в native parity.

КРИТИЧЕСКОЕ ПРАВИЛО
Не делай «похожее приложение».
Не делай новый дизайн.
Не упрощай.
Не переставляй функции.
Не заменяй сложную функцию более простой.
Не удаляй функцию потому, что её тяжело перенести.
Не «исправляй» пользовательские формулы и единицы.
Не начинай Kotlin/Compose реализацию до отдельного разрешения после Phase 0.

НА PHASE 0 ЗАПРЕЩЕНО
- менять `webapp/index.html`;
- менять текущую бизнес-логику;
- менять UI;
- создавать новые Compose screens;
- удалять WebView wrapper;
- переносить JS в Kotlin;
- менять storage schema;
- менять формулы;
- менять тексты;
- менять иконку;
- начинать рефакторинг;
- объявлять native-приложение готовым;
- ставить PASS без доказательства.

- PDF;

- settings;

J. ЗАПОЛНИ `NATIVE_MIGRATION_MATRIX.md`
На Phase 0:
- для каждой строки заполни `Web reference`;
- статус может быть только AUDITED / FAIL / UNVERIFIED;
- `Native reference` остаётся TODO/N/A;
- `Test evidence` описывает будущий точный test case;
- добавь НОВЫЕ строки для любой функции, найденной в source, которой нет в baseline matrix.

НИ ОДНА обнаруженная user-visible функция не должна остаться вне matrix.

K. ПОДГОТОВЬ NATIVE COMPONENT PLAN
Без написания native UI-кода опиши предлагаемое соответствие:
- web screen/component → native screen/component;
- web drawing engine → native drawing architecture;
- persisted model → native data model;
- modal/keypad → native component;
- backup/PDF → native implementation;
- test strategy.

Создай:
`docs/NATIVE_COMPONENT_PLAN.md`

Архитектурный ориентир:
- Kotlin;
- Jetpack Compose для обычного UI;
- dedicated native drawing layer (`CeilingDrawingView` либо Compose Canvas, если доказана точная parity);
- Room/DataStore/serializable storage — только после точной schema mapping;
- без WebView в финальном UI.

Не считай этот ориентир разрешением писать код на Phase 0.
